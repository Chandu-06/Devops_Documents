================================================================
 TERRAFORM LEARNING DOCUMENT
 Topic 09: Terraform State (terraform.tfstate)
================================================================

----------------------------------------------------------------
 WHAT IS STATE?
----------------------------------------------------------------

Terraform STATE is Terraform's memory of what infrastructure it has
already created. It is stored in a file called "terraform.tfstate".

Every time you run "terraform apply", Terraform:
  1. Creates/updates the infrastructure
  2. Saves a record of everything it created into terraform.tfstate

The next time you run "terraform plan" or "terraform apply", Terraform:
  1. Reads your .tf files (what you WANT)
  2. Reads terraform.tfstate (what ALREADY EXISTS)
  3. Compares them → calculates what needs to change

Real-life analogy:
  State = an inventory ledger in a warehouse.
  When you add or remove items, the ledger is updated.
  When the manager checks, they compare the ledger to the actual shelves.

----------------------------------------------------------------
 WHAT DOES THE STATE FILE LOOK LIKE?
----------------------------------------------------------------

terraform.tfstate is a JSON file. Example (simplified):

  {
    "version": 4,
    "terraform_version": "1.6.0",
    "resources": [
      {
        "type": "aws_instance",
        "name": "web_server",
        "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
        "instances": [
          {
            "attributes": {
              "id": "i-0abc12345678",
              "ami": "ami-0c55b159cbfafe1f0",
              "instance_type": "t2.micro",
              "public_ip": "54.203.123.45",
              "private_ip": "10.0.1.5",
              "tags": {
                "Name": "MyServer"
              }
            }
          }
        ]
      }
    ]
  }

Terraform stores EVERY attribute of every resource here.

----------------------------------------------------------------
 WHY IS STATE SO IMPORTANT?
----------------------------------------------------------------

  1. CHANGE DETECTION
     Terraform compares state vs. your code to know what to create,
     update, or destroy. Without state, it can't know what already exists.

  2. ATTRIBUTE STORAGE
     Some attributes are only known AFTER creation (e.g., IP address,
     auto-generated IDs). State stores these so you can reference them.

  3. DEPENDENCY TRACKING
     State tracks the order in which resources were created and
     their relationships.

  4. PERFORMANCE
     For large infrastructures, reading state is faster than querying
     the cloud API for every single resource each time.

----------------------------------------------------------------
 THE GOLDEN RULES OF STATE
----------------------------------------------------------------

  RULE 1: NEVER manually edit terraform.tfstate
  -----------------------------------------------
    The state file is managed exclusively by Terraform.
    Manually editing it can corrupt it and break your infrastructure management.
    Use "terraform state" commands instead (covered below).

  RULE 2: NEVER delete terraform.tfstate
  ----------------------------------------
    If you delete the state file, Terraform loses track of what it created.
    Running terraform apply again will try to CREATE everything again,
    causing DUPLICATE resources or errors.

  RULE 3: NEVER commit terraform.tfstate to Git (for sensitive data)
  -------------------------------------------------------------------
    State files contain sensitive data (passwords, keys, IPs).
    Add to .gitignore:
      terraform.tfstate
      terraform.tfstate.backup
      .terraform/

  RULE 4: Use Remote State in team environments
  -----------------------------------------------
    Local state only works for solo projects. In teams, everyone needs
    to share the same state. Use Remote State (covered next).

----------------------------------------------------------------
 LOCAL STATE vs REMOTE STATE
----------------------------------------------------------------

  LOCAL STATE (Default):
    - terraform.tfstate is saved on your laptop/server
    - Works fine for solo projects or learning
    - PROBLEM: If your laptop dies, state is gone
    - PROBLEM: Two people can't work on the same infra at the same time

  REMOTE STATE (Production/Team use):
    - State is stored in a shared remote location
    - Common backends:
        - AWS S3 bucket (most common)
        - Azure Blob Storage
        - Google Cloud Storage
        - Terraform Cloud (HashiCorp's managed service)
        - GitLab-managed Terraform state
    - Supports STATE LOCKING (prevents two people running apply simultaneously)

  Remote state configuration example (AWS S3):

    terraform {
      backend "s3" {
        bucket         = "hsbc-terraform-state-bucket"
        key            = "payment-data/dev/terraform.tfstate"
        region         = "us-east-1"
        dynamodb_table = "terraform-state-lock"    # For locking
        encrypt        = true
      }
    }

  After adding this block, run: terraform init
  Terraform will migrate the local state to S3.

----------------------------------------------------------------
 STATE LOCKING
----------------------------------------------------------------

If two people run "terraform apply" at the same time on the same state,
they could corrupt it or create conflicting resources.

STATE LOCKING prevents this by locking the state file while someone is
using it. Other users get an error: "Error: state is locked"

With AWS backend:
  - S3 stores the state file
  - DynamoDB table stores the lock

If a lock is stuck (e.g., apply was interrupted):
  $ terraform force-unlock LOCK_ID

----------------------------------------------------------------
 TERRAFORM STATE COMMANDS
----------------------------------------------------------------

These commands help you inspect and manage state safely:

  terraform state list
  ----------------------
    Lists all resources currently tracked in state.
    $ terraform state list
    Output:
      aws_instance.web_server
      aws_s3_bucket.my_bucket
      aws_vpc.main

  terraform state show
  ----------------------
    Shows all attributes of a specific resource in state.
    $ terraform state show aws_instance.web_server
    Output:
      resource "aws_instance" "web_server" {
        id            = "i-0abc12345678"
        ami           = "ami-0c55b159cbfafe1f0"
        public_ip     = "54.203.123.45"
        instance_type = "t2.micro"
        ...
      }

  terraform state mv
  -------------------
    Rename/move a resource in state (without destroying and recreating it).
    $ terraform state mv aws_instance.old_name aws_instance.new_name
    Use case: When you rename a resource in your .tf files.

  terraform state rm
  -------------------
    Remove a resource from state (Terraform forgets about it, doesn't delete it).
    $ terraform state rm aws_instance.web_server
    Use case: You want to manage this resource manually, not via Terraform.

  terraform state pull
  ---------------------
    Download the current remote state to stdout (view it).
    $ terraform state pull

  terraform state push
  ---------------------
    Upload a local state file to the remote backend.
    $ terraform state push terraform.tfstate
    WARNING: Use carefully; can overwrite remote state.

  terraform refresh
  ------------------
    Sync state with real-world infrastructure (update state to match reality).
    $ terraform refresh
    Note: In modern Terraform, plan/apply also refresh automatically.

----------------------------------------------------------------
 TERRAFORM IMPORT
----------------------------------------------------------------

What if you have existing infrastructure that was NOT created by Terraform?
You can IMPORT it into Terraform's state.

Steps:
  1. Write the resource block in your .tf file for the existing resource
  2. Run: terraform import resource_type.local_name REAL_RESOURCE_ID

Example: Import an existing EC2 instance:
  # First add this to main.tf (empty body is fine initially)
  resource "aws_instance" "legacy_server" {}

  # Then import it
  $ terraform import aws_instance.legacy_server i-0abc12345678

  # Now terraform state show aws_instance.legacy_server will show all its attributes
  # You can then fill in the resource block to match

----------------------------------------------------------------
 terraform.tfstate.backup
----------------------------------------------------------------

Every time Terraform modifies the state file, it creates a BACKUP of
the previous state in: terraform.tfstate.backup

If something goes wrong with the current state, you can restore it:
  $ cp terraform.tfstate.backup terraform.tfstate

----------------------------------------------------------------
 SUMMARY
----------------------------------------------------------------

  - State = Terraform's memory of created infrastructure (terraform.tfstate)
  - JSON file containing all resource attributes
  - NEVER manually edit, NEVER delete, NEVER commit to Git
  - Use remote state (S3/Azure Blob) for team projects
  - State locking prevents simultaneous apply conflicts
  - Use "terraform state" commands to inspect and manage state safely
  - Use "terraform import" to bring existing resources under Terraform management
